# The Home screen answers in place

Task 20 describes Home as four KPI cards, a trend row, a top-items list, and a recent-orders card "linking into Orders". It is now a five-column bento: three KPI cards, a wide Pending card carrying a meter and a way into the queue, the trend and top sellers splitting 3/2, and a full-width orders table whose rows open the order in a drawer. A pending order can be read and acted on without ever leaving the screen.

The plan was written before the repo existed and describes a dashboard that reports. What the product wanted was a dashboard you work from — the brief's words are "interactive flows, not static screens" and "edit/create flows with modals or drawers". Every difference below follows from that, and each one was a deliberate step, not drift.

**Pending left the KPI row because it is not a KPI.** The other three figures are facts about the past; Pending is a job. Sitting in a row of equal cards it read as one more number to note. Given twice the width, a meter showing its share of the book, and a button, it reads as the thing to do next. Task 20's fourth card is therefore a different component with a different type — and its tone falls back to `success` rather than `undefined` when the queue is empty, because "nothing waiting" is a state worth colouring, not an absence.

**The row keeps its shape while it loads.** Every card has a skeleton of its own dimensions, assembled by `HomeKpiRow` so the loading and loaded layouts cannot be written in two places and diverge. This is Task 20's own instruction — "skeletons appear in the card layout with no shift" — which the first implementation only honoured for the KPI row.

**A figure that counts up has to be formatted per frame.** Spec §10.1 says the screen receives display-ready strings and performs no formatting, and the count-up breaks the letter of it: `KpiCard` calls `formatFigure` on every tick as the number climbs. The rule's purpose survives intact, because the money boundary is untouched — `formatMoney` is still the only place cents become dollars, and `formatFigure` is the only caller. What moved is the *timing* of the call, not the ownership of the knowledge.

`KpiFigure` is a tagged union rather than a bare `amount: number` for the same reason: a field holding revenue must be named for cents, and one field cannot honestly be both a count of orders and a sum of money. The tween interpolates between whole cents, so `formatFigure` rounds before formatting — fractional cents exist for the length of an animation and never reach a formatter.

**The queue and the drawer are Task 21's components, reused.** Home does not own an orders table or an order drawer; it renders the ones the Orders screen renders, through `orderColumns`, so a change to how an order number or a total is drawn reaches all three tables. The dashboard's own copy had already lost Channel and Items to drift before this was fixed. Reaching across features this way is not a layering violation — an order is an order — but it does mean Home inherits Orders' action bar, and with it the transition map, which is exactly what makes a pending order actionable from here.

## Consequences

- **Task 20 is superseded by this file** for the Home screen's shape. The plan's Step 1 and Step 2 no longer describe what is there; its Step 3 — verify data, loading and error — still does, and `apps/dashboard/test/home-states.test.tsx` now covers all three.
- **[ADR 0006](0006-warm-palette-and-a-real-icon-set.md)'s consequence "the greeting on Home names nobody" no longer holds.** The header greets a named account. There is still no auth; the name comes from a hardcoded record, which is a stub with a real seam behind it and must not be mistaken for a session.
- **Per-component pixel dimensions stay literal.** The constraint "no literal pixel values in `apps/dashboard`" is about spacing, colour, radius and elevation, which are tokens. Column widths, skeleton dimensions and dialog widths have always been literals here — `OrdersTable` predates this work — and tokenising a table column would be a token per column. The rule as written is broader than the repo has ever followed; read it as "no literal *token* values".
- **The chart's entrance depends on the frame clock.** `frameClockRuns()` decides whether the bars stage an entrance or paint outright, so in a tab that has never been foregrounded the chart is correct and still. Same for `useCountUp`'s failsafe. Anything else that animates from nothing should ask the same question — an entrance that begins at zero and never runs is a blank screen, not a slow one.
